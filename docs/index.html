50 interview questions & answers (case-based) — click any question to expand; filter by topic

1. How do you choose between Fable, Opus, Sonnet, and Haiku?
Fable 5.2 is the most capable model — reach for it on the hardest reasoning and long-horizon agentic work. Opus 5.5 is the most capable Opus tier — highly autonomous coding, knowledge work, and memory. Sonnet 5.5 balances intelligence and cost — near-Opus quality at Sonnet price, the default for most production workloads and agents. Haiku 5.5 is fastest and cheapest — ideal for classification, routing, and sub-agent roles. Strategy: start with Sonnet 5.5, escalate to Opus 5.5 or Fable 5.2 where evals show quality gaps, downgrade to Haiku where latency or cost dominates.
2. How does prompt caching work and when should you use it?
Mark stable prefix content — system instructions, large documents, tool definitions — with a cache_control breakpoint. Anthropic stores that prefix server-side and serves later requests with the same prefix at reduced input token cost and lower latency. Use it whenever you have repeated large context: RAG systems, agentic loops with stable tool schemas, and multi-turn chats with fixed system prompts. Cache TTL is 5 minutes by default, refreshed on each hit.
3. Why does Anthropic recommend XML tags in prompts?
Claude is trained to treat XML as semantic structure. Wrapping content in tags like , , clearly separates context, examples, task, and output requirements. This reduces ambiguity, improves instruction following, and makes outputs easier to parse programmatically when you ask Claude to respond inside specific tags.
4. How do you reduce hallucinations in Claude's outputs?
Compound several techniques: (1) provide source material in the prompt and instruct Claude to cite it, (2) give Claude explicit permission to say "I don't know," (3) ask it to reason step-by-step before answering, (4) enable extended thinking for complex reasoning, (5) ground claims via retrieval, (6) run judge-model evals and tune. The strongest intervention is usually giving Claude the information it needs rather than relying on parametric memory.
5. What's the difference between system messages and user messages?
The system parameter sets persistent behavior, role, constraints, and tone — outside the messages array. The messages array holds alternating user/assistant turns. Best practice: stable instructions, persona, output format, and policies go in system; actual tasks, data, and conversation history go in messages. System content also caches well.
6. What is CLAUDE.md and why does it matter?
CLAUDE.md is a project memory file Claude Code reads automatically at session start. Put your project's architecture, coding conventions, key directories, important commands, and team rules inside it. Every new conversation begins with this context loaded — eliminating repetitive setup. A user-level file lives at ~/.claude/CLAUDE.md; project-level files override user-level.
7. How do you optimize token usage in long Claude Code sessions?
Use /compact to summarize prior context instead of /clear when you want to keep a thread. Write precise prompts targeting specific files. Move recurring instructions into CLAUDE.md. Limit simultaneously enabled MCP servers — too many tool definitions can shrink usable context from 200K to under 100K tokens. Use sub-agents for isolated explorations that would otherwise pollute the main session.
8. What are hooks in Claude Code and what are they used for?
Hooks are shell commands triggered by Claude Code lifecycle events — before/after a tool call, before a commit, on session start. Use them to enforce linting, run tests, log actions for audits, block dangerous commands, or notify CI systems. They're defined in settings.json and let you wrap Claude's autonomy in deterministic guardrails.
9. What is Model Context Protocol (MCP)?
MCP is an open standard for connecting AI agents to external tools and data sources. An MCP server exposes tools, resources, and prompts; a client (Claude Code, the API's MCP connector, or the Claude.ai interface) discovers and calls them. Transports include stdio (local processes), SSE, and HTTP. It eliminates one-off integrations — any MCP-compliant server works with any MCP-compliant client.
10. How would you secure an MCP server in production?
Treat MCP servers like any privileged subprocess: install only from trusted sources, use scoped credentials with minimum required permissions, store secrets in env vars or a secrets manager (not plaintext configs), enable structured logging for all tool calls, restrict network egress, and run processes in isolated containers for high-risk integrations. Pin server versions to avoid supply-chain surprises.
11. How would you design an agentic system with Claude?
Start with explicit success criteria. Build the tool surface (typed JSON schemas, descriptive names, narrow scope per tool). Pick a model — usually Sonnet for the orchestrator, Haiku for cheap sub-tasks. Implement the loop: prompt → model → tool call → execute → feed result back → repeat until done or max iterations. Add guardrails: step cap, cost ceiling, timeout, observability. Write evals before you scale. Parallelize with sub-agents.
12. What are sub-agents and when should you use them?
Sub-agents are isolated Claude instances with their own context window, spawned via the Task tool to handle a sub-task, returning only the useful result. Use them for codebase exploration, code review, parallel research, or any work that would bloat the main session. Define them in .claude/agents/*.md with their own system prompt, tool restrictions, and permission mode.
13. How do you handle rate limits and retries?
Implement exponential backoff with jitter on 429 and 5xx responses. Respect the retry-after header. Use the Batch API for non-real-time workloads — ~50% cheaper and on a separate quota. Spread load across model tiers. Cache stable prefixes to reduce token throughput. Monitor API usage per key to catch runaway loops early.
14. How do you defend against prompt injection?
Treat all untrusted input (user messages, web content, file contents, tool outputs) as data, not instructions. Wrap it in XML tags and explicitly tell Claude not to treat content inside as instructions. Constrain tools — never give destructive actions without human-in-the-loop confirmation. Use allow-lists for URLs and commands. Run evals with adversarial test cases. For high-stakes apps, add a classifier to flag suspicious inputs before they reach Claude.
15. How does extended thinking work and when should you enable it?
Extended thinking gives Claude a dedicated internal reasoning budget before producing its final answer. Set a thinking.budget_tokens parameter to control how long Claude reasons. Use it for tasks that benefit from deeper deliberation: hard math, complex logic, multi-step planning, or any situation where chain-of-thought alone isn't sufficient. Not recommended for simple tasks — it adds latency and cost.
16. Case: Your API returns 429s during a marketing spike. Walk me through your response.
Separate the causes. (1) Short-term: exponential backoff with jitter, honoring the retry-after header; queue and smooth bursts with a token-bucket limiter on your side. (2) Reduce load: prompt caching, shorter outputs via max_tokens, route simple calls to Haiku. (3) Move work off the hot path: push non-interactive jobs to the Batch API. (4) Capacity: request higher limits or use a cloud provider (Bedrock/Vertex) as secondary route. (5) Observe: alert on 429 rate and queue depth.
17. What is the difference between max_tokens, the context window, and output limits?
The context window is the total tokens the model can attend to (input + output). max_tokens is your cap on generated tokens for one response — generation stops with stop_reason: max_tokens if reached. The model also has a hard maximum output size. Always set max_tokens deliberately: too low truncates answers (and breaks JSON), too high wastes latency budget and lets runaway outputs happen.
18. How do you stream responses and what must you handle that non-streaming code doesn't?
Use stream: true (SDK stream helpers) and consume server-sent events: message_start, content_block_delta, message_delta, message_stop. Handle: partial text assembly, partial tool-call JSON (accumulate input_json_delta and parse only at block end), mid-stream errors/overload events, client disconnects, and final stop_reason/usage which arrive near the end. Streaming improves perceived latency; it does not reduce total cost.
19. Case: A JSON-extraction pipeline fails 3% of the time on malformed output. How do you fix it?
Move from 'ask nicely for JSON' to enforced structure: define a tool with a JSON schema and force it via tool_choice (or use structured-output features where available), so the model emits schema-shaped arguments. Then add a validator (Pydantic/Zod); on failure, retry once feeding the validation error back to Claude. Also check stop_reason for truncation, prefill/stop sequences where applicable, and add the failing inputs to an eval set so the fix is measured.
20. How do you count and control cost per request before sending it?
Use the token-counting endpoint to measure input tokens for a full request (system, tools, messages, images) without running it. Multiply by per-model prices, add expected output tokens. Control cost via: cache stable prefixes, trim history (summaries), cap max_tokens, choose the smallest adequate model, batch offline work, and log usage (including cache read/write tokens) per request to attribute spend by feature or tenant.
21. When would you choose the Batch API, and how do you design around it?
Choose it for latency-tolerant, high-volume work: evals, backfills, classification of archives, content generation, nightly enrichment. It is priced lower than real-time and completes asynchronously (up to ~24h). Design: idempotent custom_id per item, store inputs durably, poll or webhook for completion, map results by custom_id, handle per-item errors/expiry with a re-submit path. Never use it for anything a user is waiting on.
22. How do you send images or PDFs to Claude, and what are the gotchas?
Add image or document content blocks (base64 or URL/file reference) before the text question. Gotchas: images and PDF pages consume tokens (cost scales with size/pages), resolution is downscaled above limits so tiny text may be lost, put the media before the question for best results, label multiple images, and for long PDFs consider chunking or the Files API plus caching to avoid resending.
23. What does stop_reason tell you and how should your code branch on it?
end_turn: natural finish. max_tokens: truncated — raise the cap or continue the turn. tool_use: execute tools and return tool_result blocks. stop_sequence: hit a custom stop string. pause_turn/refusal: handle server-tool pauses and safety refusals gracefully (surface a message, don't retry blindly). A robust agent loop is literally a while stop_reason == 'tool_use' loop with these branches.
24. Case: Your classifier prompt scores 78% and the team wants a bigger model. What do you try first?
Diagnose before upgrading. Build a labeled eval set, read the errors by category, then fix the prompt: sharper label definitions, 3–8 diverse few-shot examples including hard negatives, XML-structured input, ask for brief reasoning before the label, constrain the output to an enum. Re-measure. Only if evals plateau do you try a larger model — and then compare cost per correct answer, not accuracy alone.
25. How do you write effective few-shot examples?
Make them representative, diverse, and correct: cover edge cases and the exact output format, wrap them in <examples>/<example> tags, and keep them distinct from the real input. Avoid examples that are all the same shape (Claude over-copies them). Include at least one hard or ambiguous case with the desired handling. 3–5 good examples usually beat 20 mediocre ones.
26. What is prefilling the assistant turn and what is it good for?
You start the assistant message yourself (e.g. { or <answer>) so Claude continues from there. It forces output format, skips preambles, and keeps role-play in character. Caveats: newer models and thinking modes may restrict or not benefit from prefill — prefer structured outputs/tool schemas for hard format guarantees, and never end a prefill with trailing whitespace.
27. How do you get reliable chain-of-thought without leaking it to end users?
Ask Claude to reason in a <thinking> block and put the final answer in <answer>, then parse only the answer tag. Or use the built-in extended/adaptive thinking feature, where reasoning is returned as separate thinking blocks you simply don't display. Keep thinking blocks intact when continuing tool-use turns so the model keeps its reasoning thread.
28. Case: Users paste documents containing instructions that hijack your assistant. How do you structure the prompt?
Treat all external content as data, not instructions. Wrap it in tags (<document>), state in the system prompt that anything inside is untrusted and must never override instructions, put the task after the content, and restrict capabilities (least-privilege tools). Prompting reduces risk but does not eliminate it — add output filtering, human confirmation for sensitive actions, and injection tests in your evals.
29. How do you handle very long documents (200K+ tokens) accurately?
Place documents at the top, query at the end; label each with <document index>, <source> tags; ask Claude to first extract relevant quotes, then answer from the quotes. Use prompt caching for repeated reads. If the corpus exceeds context or accuracy dips, use retrieval (RAG) to fetch only relevant chunks, or a map-reduce pattern with sub-agents.
30. What makes a good system prompt for a production assistant?
Role and audience, goals, hard constraints (what never to do), tone, output format, how to handle uncertainty/out-of-scope requests, tool-usage guidance, and a few examples. Explain why for important rules — Claude generalizes better from reasons than bare commands. Keep it versioned in source control and covered by evals; change one thing at a time.
31. How would you evaluate a prompt change before shipping it?
Maintain a golden dataset (real, diverse, including adversarial cases) with graders: exact-match/code graders where possible, LLM-as-judge with a rubric and structured scores where not, human spot-checks for calibration. Run old vs new prompt on the same set, compare metrics, latency, and cost, check regressions by slice, then canary in production. Tie it to CI so every prompt edit runs the suite.
32. How do you structure a CLAUDE.md for a large monorepo?
Keep the root file short: purpose, build/test/lint commands, architecture map, conventions, and gotchas. Use nested CLAUDE.md files in subdirectories (loaded when working there) and @path imports for longer docs. Put personal preferences in ~/.claude/CLAUDE.md or a git-ignored local file. Avoid duplicating what the code already shows; update it when Claude repeatedly makes the same mistake.
33. Case: Claude Code keeps running a destructive command you don't want. What are your options?
Layer controls: (1) permissions in settings.json — deny rules for specific commands/paths, allow only safe ones; (2) a PreToolUse hook that inspects the tool call and blocks with a message; (3) run in a sandbox/container or a git worktree; (4) keep default permission mode so it asks before risky actions; (5) add the rule to CLAUDE.md as guidance. Deterministic enforcement belongs in permissions/hooks, not in prose.
34. What are custom slash commands and skills, and how do they differ?
Slash commands are reusable prompt templates stored as markdown (project or user scope) invoked explicitly with /name, supporting arguments. Skills are folders with a SKILL.md plus scripts/resources that Claude can discover and load on demand based on their description — progressive disclosure keeps context small. Use commands for explicit workflows you trigger; skills for capabilities Claude should pull in itself.
35. How does Claude Code run in CI/headless mode and what do you watch for?
Use print/headless mode (claude -p) with --output-format json or streaming JSON, a scoped tool allowlist, and a max-turns budget. Provide secrets via env, never in prompts. Watch for: non-interactive permission prompts (pre-approve narrowly), cost/turn caps, idempotency, posting results as PR comments, and treating repo content as untrusted input (prompt-injection risk in PRs from forks).
36. Case: A session degrades after hours of work — repeated mistakes, forgotten decisions. What do you do?
Context has bloated or drifted. Use /compact with focus instructions, or better, write decisions/progress to a file (plan.md / notes) and start a fresh session with /clear that loads it. Delegate noisy exploration to sub-agents so their output stays out of the main context. Keep CLAUDE.md lean, and break big tasks into checkpointed steps.
37. How do you use plan mode and when is it worth it?
Plan mode makes Claude research and propose a plan without editing files or running mutating commands, so you can review and correct approach before any change. Use it for multi-file refactors, unfamiliar code, migrations, and anything ambiguous or risky. It front-loads cheap thinking and prevents expensive wrong implementations.
38. Case: You need Claude to read Jira, query a warehouse, and post to Slack. Design the MCP layer.
One focused MCP server per system (or vetted existing ones), each exposing a small set of well-named, well-described tools with narrow schemas. Auth per server using scoped, short-lived credentials (OAuth where possible); read-only credentials for the warehouse; write tools gated behind confirmation. Set tool allowlists per agent so each only sees what it needs. Log every call, apply timeouts/rate limits, and test tool descriptions with evals.
39. What are the three MCP primitives and how do they differ?
Tools — model-controlled actions the LLM chooses to call. Resources — application-controlled read-only context (files, records) addressed by URI. Prompts — user-controlled reusable templates surfaced as commands. The distinction is who decides to invoke: model, app, or user.
40. Compare stdio and streamable HTTP transports for MCP.
stdio: the client launches the server as a local subprocess — simple, no network, ideal for local dev tools, one client per process. Streamable HTTP: a remote server over HTTP (with optional streaming) — supports many clients, centralized auth (OAuth), deployment and monitoring. Choose stdio for local/personal tooling, HTTP for shared, multi-user, production servers.
41. How should MCP tools report errors so the model can recover?
Return a tool result flagged as an error with an actionable, human-readable message (what failed, why, what to try) rather than throwing or returning an empty result. Distinguish retryable (timeout, rate limit) from non-retryable (invalid argument, not found) failures and include valid-value hints. Claude can then self-correct or escalate instead of looping.
42. What is the risk of connecting many MCP servers at once?
Tool-definition bloat consumes context and degrades tool selection; overlapping tool names confuse routing; every server expands the attack surface (malicious descriptions/'tool poisoning', exfiltration via a permissive tool combination). Mitigate by loading only needed servers per task, using tool search/deferred loading, namespacing, auditing third-party servers, and applying least-privilege per agent.
43. Case: Design a customer-support agent that can issue refunds. Where do you put humans in the loop?
Tiered autonomy: read-only lookups and answers are automatic; refunds under a threshold with policy-verified eligibility are automatic with logging; larger or ambiguous refunds go to an approval queue with Claude's evidence summary. Enforce limits in the tool/back-end (not the prompt), validate idempotency keys, escalate on low confidence, repeated user frustration, or policy conflict, and audit every action.
44. Orchestrator-workers vs. a single agent with many tools — how do you decide?
Start single-agent: simpler, cheaper, easier to debug. Move to orchestrator-workers when subtasks are parallelizable, need different contexts/tools/permissions, or a single context would overflow. Multi-agent costs more tokens and adds coordination failures, so justify it with eval gains. Give workers narrow instructions and have them return concise structured summaries.
45. How do you make an agent resilient to tool failures and long-running tasks?
Timeouts and retries with backoff per tool, structured errors fed back to the model, loop/turn/budget caps, checkpointing state externally (database/file) so work resumes after crash, idempotent side effects, and a final verification step. For long jobs, persist a progress file or task list so a fresh context can pick up where the last stopped.
46. How do you evaluate an agent, not just a single prompt?
Evaluate trajectories and outcomes: task success on a scenario suite (often with a sandboxed environment and programmatic end-state checks), tool-call correctness, number of steps/tokens/latency, safety violations, and recovery from injected failures. Use LLM judges for qualitative criteria with rubrics, replay real transcripts, and run each case several times since agents are non-deterministic.
47. What is context engineering for agents?
Deliberately curating what is in the window at each step: concise system prompt, only relevant tools, retrieved snippets over whole files, summaries of old turns, clearing stale tool results, and external memory (files/notes) for durable facts. Goal: the smallest set of high-signal tokens that lets the model make the next decision well.
48. Case: Two sub-agents return conflicting findings. How should the orchestrator resolve it?
Don't silently pick one. Require workers to return claims with evidence/sources and confidence; have the orchestrator compare, ask a verifier sub-agent (or tool-based check) to test the disputed claim, and report remaining uncertainty explicitly in the final answer. Log conflicts as signals for improving worker prompts.
49. How do you design multi-tenant isolation when many customers share one Claude integration?
Never mix tenants in one context. Scope retrieval and tools by tenant ID enforced in code, use per-tenant cache prefixes (cache is keyed by prefix content), separate API keys/workspaces for cost attribution and rate-limit isolation where needed, redact PII, and log usage per tenant. Test with cross-tenant leakage cases in your evals.
50. What are Anthropic's data-handling and safety considerations you must mention to an enterprise buyer?
Cover: zero-data-retention options and commercial terms on training use, region/data-residency choices via cloud providers, encryption, access controls and audit logging on your side, PII minimization/redaction, content filtering and abuse monitoring, compliance attestations, and the shared-responsibility split between Anthropic, the cloud platform, and the customer. Cite the current Anthropic trust documentation rather than assuming.

These are unofficial study questions modeled on official exam domains. Study the Anthropic Academy courses and docs.claude.com as your authoritative source.
Q1. Your customer-support agent handles 10K live conversations/day with a stable 5K-token system prompt. Which single feature most reduces your API cost?
Answer: Prompt caching. Mark the stable system prompt (and tool definitions) with a cache_control breakpoint. Cache hits dramatically reduce input token cost. The Batch API is cheaper still but only for async/offline workloads — live customer support requires real-time responses.
Q2. Which file does Claude Code automatically load at session start to provide project context?
Answer: CLAUDE.md. Claude Code reads CLAUDE.md from the project root (and ~/.claude/CLAUDE.md at user scope) at session start. It's the canonical location for conventions, architecture notes, and standing instructions.
Q3. What's the correct way to connect a remote MCP server directly via the Anthropic Messages API?
Answer: Use the MCP connector with the beta header anthropic-beta: mcp-client-2025-11-20 and pass the server URL in the mcp_servers parameter. This connects to remote MCP servers without needing a separate MCP client process running locally.
Q4. You're using Claude as a grader to evaluate another Claude's responses. What should you ask the grader to return for reliable scores?
Answer: Strengths, weaknesses, detailed reasoning, and a numerical score. Bare numbers produce near-random results. Requiring written justification forces the grader to engage with the content, producing consistent, defensible scores. This is the pattern Anthropic's evaluation guidance recommends.
Q5. Which Claude Code feature delegates a sub-task to an isolated context window that returns only its output?
Answer: Sub-agents. Defined in .claude/agents/*.md with their own system prompt, tool restrictions, and permission mode. Activated via the /agents command or the Task tool. They run with an independent context window and return only the useful result to the main session.
Q6. What's the most effective way to show Claude exactly what output format you want?
Answer: Few-shot examples. Provide one or more concrete output examples, ideally wrapped in tags. Concrete examples beat abstract format descriptions for adherence. Even a single high-quality example produces large gains in output consistency.
Q7. Which slash command compresses Claude Code conversation history while preserving a summary?
Answer: /compact. Unlike /clear (wipes all context), /compact summarizes prior turns and replaces them with the summary — typically reducing token usage 40–60% on long sessions while keeping the thread alive.
Q8. You need Claude Code to query a private Postgres database. What's the architecturally correct approach?
Answer: Build or install a Postgres MCP server that exposes database operations as MCP tools. Register it in settings.json at the appropriate scope (user, project, or local) with scoped credentials. This follows Anthropic's open standard and integrates cleanly with Claude Code's tool discovery.
Q9. Your agentic loop is making runaway tool calls. What's the first guardrail to add?
Answer: A maximum step / iteration cap. Pair it with a cost ceiling and timeout. Then add observability (log every tool call), evals on adversarial inputs, and human-in-the-loop confirmation for destructive or irreversible actions. Step caps are the cheapest, fastest-to-implement first line of defence.
Q10. Which model is best for high-volume, low-complexity classification at the lowest cost?
Answer: Claude Haiku 5.5. Fastest and cheapest current Claude model with near-frontier intelligence — designed for high-throughput classification, routing, simple extraction, and sub-agent roles where Sonnet or Opus would be overkill.
Q11. What does "tool use" mean in the Anthropic API and how does the loop work?
Answer: Tool use (function calling) lets you define JSON-schema-described tools. Claude returns a tool_use block when it wants to call one; your code executes the tool and feeds back a tool_result message. The model continues until it returns a final text answer with no further tool calls. Loop control (max turns, cost caps) is your responsibility.
Q12. What's the most important practice when designing tools for an agent?
Answer: Clear, descriptive tool names and descriptions with narrow scope per tool. Claude's tool selection accuracy depends heavily on tool metadata. Avoid mega-tools that do many things. Prefer focused tools with informative descriptions and explicit input schemas. Vague or overlapping tool descriptions are the leading cause of agentic failures.
Q13. How do you debug a silently failing MCP connection in Claude Code?
Answer: Launch Claude Code with --mcp-debug and run /mcp in-session to inspect server status. This surfaces handshake errors, authentication failures, and transport-level issues that aren't visible by default. Also check claude mcp list to verify configured servers.
Q14. Where should you place a coding convention you want shared with the whole team on every Claude Code session?
Answer: CLAUDE.md at the project root, committed to version control. Project-scope CLAUDE.md overrides user-scope and is shared via the repo — exactly the right pattern for team-wide conventions. User-scope (~/.claude/CLAUDE.md) is for personal preferences only.
Q15. The Batch API offers what tradeoff compared to the real-time Messages API?
Answer: ~50% lower cost in exchange for asynchronous, non-real-time completion. Submit a batch of requests; results return within a service window (up to 24 hours). Ideal for offline pipelines, evaluations, bulk data analysis, and labeling tasks where immediate responses aren't needed.
Q16. [Agentic] A research agent loops forever, re-searching the same query. Which fix addresses the root cause?
Answer: Add loop controls AND make failures informative. Cap turns/tool calls and detect repeated identical calls, but also return structured tool results that say 'no new results' so the model changes strategy. A max-turn limit alone only stops the symptom.
Q17. [Agentic] When is a multi-agent (orchestrator + workers) design most justified over a single agent?
Answer: When subtasks are independent/parallelizable or need separate contexts and permissions. Otherwise a single agent is cheaper, simpler, and easier to debug; multi-agent adds token cost and coordination failure modes.
Q18. [Agentic] Where should a hard business rule such as 'refunds over $500 need approval' be enforced?
Answer: In the tool/backend code (deterministic enforcement). Prompts are guidance and can be bypassed by injection or error; the refund tool itself must reject or route over-limit requests to approval.
Q19. [Agentic] An agent's tool returns a 40K-token JSON blob each call and quality drops. Best fix?
Answer: Make the tool return only what's needed — filter fields, paginate, summarize, or return IDs with a detail-fetch tool. Large irrelevant tool output crowds the context and degrades reasoning.
Q20. [Agentic] Which pattern fits a workflow whose steps are known in advance (extract → validate → format)?
Answer: Prompt chaining / a fixed workflow. Use deterministic orchestration in code with an LLM call per step; reserve autonomous agents for open-ended tasks where steps can't be predetermined.
Q21. [Agentic] How should an agent handle an ambiguous user request that could trigger an irreversible action?
Answer: Ask a clarifying question or request confirmation before acting. Cost of one extra turn is small compared to an irreversible wrong action; pair with least-privilege tools.
Q22. [Claude Code] You want a safety check that ALWAYS runs before any shell command. Which mechanism?
Answer: A PreToolUse hook (matching the Bash tool) that can inspect and block the call. Hooks run deterministically; CLAUDE.md instructions are advisory.
Q23. [Claude Code] Where do team-shared project permissions and MCP servers belong, so they are version-controlled?
Answer: Project-scoped config committed to the repo (.claude/settings.json, .mcp.json); personal overrides go in the local/user settings that are not committed.
Q24. [Claude Code] A sub-task needs to read 200 files and report one conclusion. Best approach?
Answer: Delegate to a sub-agent so the file reads stay in its isolated context and only the conclusion returns to the main session.
Q25. [Claude Code] What does /clear do versus /compact?
Answer: /clear resets the conversation context entirely; /compact replaces history with a summary (optionally guided by instructions) so you keep continuity at lower token cost.
Q26. [Claude Code] You need different Claude Code behavior for the frontend/ directory only. What's the cleanest approach?
Answer: A nested CLAUDE.md inside frontend/ — loaded when working in that subtree — rather than bloating the root file.
Q27. [Claude Code] Why use git worktrees with parallel Claude Code sessions?
Answer: Each session gets its own working directory and branch, so parallel agents don't overwrite each other's file edits.
Q28. [Claude Code] A hook must run after every file edit to auto-format. Which event?
Answer: PostToolUse matched on edit/write tools — it runs after the tool completes, ideal for formatters and linters.
Q29. [API] You need guaranteed schema-valid output for downstream code. Most reliable approach?
Answer: Tool use with a JSON schema (forced via tool_choice) or native structured outputs, plus validation and retry. Plain 'please return JSON' instructions are the least reliable.
Q30. [API] What does a response with stop_reason: "tool_use" require from your code?
Answer: Execute the requested tool(s) and send back tool_result blocks (matching tool_use_id) in a user message, then call the API again to continue.
Q31. [API] The conversation grows and each call re-sends 80K tokens of history. Which combination cuts cost most?
Answer: Prompt caching on the stable prefix plus summarizing/trimming old turns. Caching lowers cost of repeated prefix; trimming reduces what you send at all.
Q32. [API] How do you let Claude call your function AND keep your API key out of the model's context?
Answer: Define the function as a tool; your server executes it with the secret and returns only the result. Secrets never go in prompts or tool results.
Q33. [API] A long, stable block of reference docs is prepended to every request. Where do you put the cache_control breakpoint?
Answer: At the end of the stable block (before the variable content). Caching matches an exact prefix, so volatile content (user question, timestamps) must come after it.
Q34. [API] What causes a prompt-cache miss that surprises teams?
Answer: Any change in the cached prefix — a timestamp in the system prompt, reordered tools, or edited text — or exceeding the cache TTL. Keep prefixes byte-stable.
Q35. [Prompting] What's the most effective placement for a long document and the question?
Answer: Document first (tagged), question at the end. Queries placed after long context measurably improve response quality.
Q36. [Prompting] Claude over-copies your single few-shot example. Fix?
Answer: Provide several diverse examples (different shapes and lengths, including edge cases) so it learns the pattern rather than the surface form.
Q37. [Prompting] You want brief answers without preamble. Which instruction style works best?
Answer: Say what to do, with the reason ('Reply with only the category name; it is parsed by a script') rather than only what not to do.
Q38. [Prompting] How should you make Claude cite sources from provided documents?
Answer: Ask it to first extract verbatim quotes in tags, then answer referencing those quotes (or use the citations feature). Grounding in quotes reduces fabrication.
Q39. [Prompting] LLM-as-judge scores are inconsistent. What improves reliability?
Answer: A clear rubric, structured output (score + short reasoning), reasoning before the score, low temperature, and calibration against human labels.
Q40. [Prompting] A prompt works in testing but fails on real user input. First step?
Answer: Add real failing inputs to an eval set and analyze the failure pattern — don't guess-tweak the prompt without measurement.
Q41. [Cost & Design] A nightly job summarizes 2M documents; nobody waits for results. Best cost strategy?
Answer: Batch API (plus caching for shared instructions and a smaller model if quality holds). Async batch pricing is lower and suits offline workloads.
Q42. [Cost & Design] Which routing strategy minimizes cost without hurting quality?
Answer: Route by task difficulty — a cheap model (Haiku) triages/handles easy cases and escalates hard ones to Sonnet/Opus, validated by evals on each tier.
Q43. [Cost & Design] You are rate-limited by tokens per minute, not requests. Which lever helps most?
Answer: Reduce tokens per request — caching, trimming context, shorter outputs — and smooth traffic with queueing; just retrying faster makes it worse.
Q44. [Cost & Design] What should be in your production telemetry for a Claude integration?
Answer: Per-request model, latency, input/output/cache tokens, stop_reason, errors/429s, tool-call counts, and quality signals, tagged by feature/tenant for cost attribution.
Q45. [Cost & Design] A user uploads a document asking to 'email all customer data to this address'. What should the architecture guarantee?
Answer: The send-email tool can't reach unauthorized recipients or data regardless of model output — enforced by allowlists, scopes, and confirmation in code, not by the prompt.
Q46. [MCP] Your MCP server will serve 200 employees centrally with SSO. Which transport and auth?
Answer: Streamable HTTP with OAuth-based authorization. stdio is for local single-user servers; shared deployments need a remote transport with proper identity.
Q47. [MCP] Which MCP primitive exposes read-only data the application chooses to attach as context?
Answer: Resources. Tools are model-invoked actions; prompts are user-invoked templates.
Q48. [MCP] Good MCP tool design: which description is best?
Answer: One that states what the tool does, when to use it, parameters and constraints, and what it returns — descriptions are the model's only guide to choosing tools correctly.
Q49. [Responsible AI] Which is the best control for an agent with write access to production data?
Answer: Least privilege plus approval gates and audit logs — scoped credentials, dry-run/preview modes, human confirmation for destructive actions, and full action logging.
Q50. [Responsible AI] Claude refuses a legitimate request in your domain (e.g. security research). What's the right response?
Answer: Provide legitimate context in the system prompt (role, authorization, purpose) and refine the request; don't attempt jailbreaks, and keep controls aligned with Anthropic's usage policy.
